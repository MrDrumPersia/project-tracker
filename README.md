# پروژه‌یار V3 — برنامه اجرا و انتشار ایمن

## هدف
بازطراحی رابط کاربری Project Tracker بر اساس نسخه موجود با حفظ ذخیره‌سازی در `data/projects.json` از طریق Vercel Function و GitHub Contents API. تغییر محیط میزبانی، ساخت پروژه جدید در Vercel یا متغیر محیطی جدید لازم نیست.

## شش قابلیت پیاده‌سازی‌شده

| بخش | قابلیت | رفتار اصلی |
|---|---|---|
| امروز من | فهرست کارهای امروز و عقب‌افتاده | وظایف دارای سررسید امروز یا قبل، همراه با صف کارهای بدون سررسید و امکان برنامه‌ریزی برای امروز |
| برد کانبان | سه ستون وضعیت | انتقال با Drag & Drop در دسکتاپ یا منوی وضعیت در موبایل؛ ثبت فوری در GitHub |
| اولویت‌بندی | فوری، بالا، عادی، پایین | اولویت هر وظیفه، سررسید، فیلتر و نمایش بصری در کارت‌ها |
| تکرارشونده | روزانه / هفتگی / ماهانه | تعریف الگو، توقف/فعال‌سازی، تولید دستی نوبت‌های رسیده با پیشگیری از تکرار |
| گزارش پیشرفته | تحلیل وضعیت | KPI، نمودار ۷ روز اخیر (پس از V3)، نرخ تکمیل، پیشرفت پروژه‌ها، خروجی CSV و چاپ/PDF مرورگر |
| تاریخچه و بازیابی | تاریخچه پروژه | ثبت ۲۵ رویداد اخیر برای هر پروژه همراه با Snapshot، بازگردانی یک نسخه، بایگانی قابل بازگردانی، دانلود JSON پشتیبان |

## معماری / سازگاری

```
Browser (index.html)
       |
       | GET/POST /api/projects  => JSON Array
       v
Vercel Serverless Function (api/projects.js)
       |
       | GH_TOKEN موجود
       v
GitHub Contents API -> data/projects.json
```

* فرمت ریشه همچنان **آرایه پروژه‌ها** است. داده‌های قدیمی هنگام `GET` بدون تغییر خوانده می‌شوند و در شروع برنامه هیچ ذخیره خودکاری انجام نمی‌شود.
* فیلدهای قبلی هر پروژه (`id`, `name`, `start`, `end`, `progress`, `tasks`, `note`) حفظ می‌شوند. فیلدهای افزوده: `history`, `recurring`, `archived`, `updatedAt`. فیلدهای افزوده وظیفه: `id`, `priority`, `due`, `status`, `completedAt`, `createdAt`, `deletedAt`, `sourceRecurringId`.
* تاریخ‌های ذخیره‌شده همچنان ISO Gregorian هستند؛ برای کاربر **انتخاب و نمایش تاریخ شمسی** ارائه می‌شود.
* API همان GET/POST قبلی را حفظ می‌کند. برای جلوگیری از بازنویسی ناخواسته، `GET` هدر `X-Data-Sha` و `POST` هدر اختیاری `X-Expected-Sha` را پشتیبانی می‌کند؛ در تغییر هم‌زمان، وضعیت `409` برگردانده می‌شود. کلاینت‌های قدیمی که هدر را نمی‌فرستند همچنان کار می‌کنند، اما از محافظ تداخل بهره نمی‌برند.
* تمام جهش‌ها پس از پاسخ موفق API در رابط اعمال می‌شوند. اگر API قطع شود یا ذخیره شکست بخورد، داده سرور بازنویسی و نسخه داخلی جایگزین نمی‌شود.

## انتشار روی GitHub و Vercel

1. در مخزن GitHub فعلی از `data/projects.json` یک نسخه پشتیبان بگیرید؛ اگر برنامه عملیاتی است، نسخه **واقعاً به‌روز** را از خود GitHub بردارید، نه ZIP قدیمی.
2. در همان شاخه‌ای که Vercel در حال Deploy آن است، فقط **دو فایل** را جایگزین کنید: `index.html` در ریشه و `api/projects.js` در پوشه API. فولدر `data/` را دست نزنید.
3. هر دو تغییر را ترجیحاً در یک Commit وارد کنید. از GitHub Desktop یا Git محلی برای ثبت هم‌زمان استفاده کنید.
4. اگر پروژه فعلی Vercel به همین شاخه وصل است و `GH_TOKEN` موجود و معتبر است، Deploy خودکار انجام خواهد شد. نیازی به ورود به داشبورد Vercel یا تعریف متغیر جدید نیست.
5. پس از انتشار، از صفحه وب `GET /api/projects` و سپس ایجاد/تغییر یک **وظیفه آزمایشی غیرحساس** را امتحان کنید. با یک مرورگر دیگر تغییر هم‌زمان را تست کنید؛ در صورت تداخل پیام «نسخه تغییر کرده» باید ظاهر شود.
6. اگر مشکلی پیش آمد، با **Revert** دو فایل کد به Commit قبلی برگردید. داده‌های `data/projects.json` را با نمونه‌های همراه این فایل جایگزین نکنید.

> ZIP انتشار فقط `index.html`, `api/projects.js`, `README.md` را دارد. فایل‌های واقعی `data/projects.json` و توکن در آن وجود ندارند.

## سناریوهای آزمون

- دریافت ۳۱ پروژه و ۷۴ وظیفه از **کپی آفلاین** ساختار پروژه فعلی بدون `POST` هنگام بارگذاری؛ ساخت وظیفه جدید بدون حذف داده‌های موجود.
- نمایش داشبورد، امروز، برد کانبان، کارهای تکراری، گزارش و تاریخچه در مرورگر Chromium با داده نمونه؛ بدون خطای JavaScript.
- ثبت وظیفه جدید، تولید نوبت‌های تکراری، فیلترها، باز کردن جزئیات؛ بررسی عدم اسکرول افقی کل صفحه در موبایل ۳۹۰ پیکسل.
- شبیه‌سازی تغییر SHA در GitHub پیش از ذخیره: واکنش 409 و حفظ نسخه قدیمی.
- آزمون نهایی روی Vercel واقعی **هنوز انجام نشده** چون به محیط عملیاتی دسترسی نداریم.

## محدودیت‌ها و ریسک‌ها

1. **امنیت:** API اولیه احراز هویت اپلیکیشنی ندارد؛ هر شخصی که به آدرس قابل دسترس `/api/projects` برسد، بالقوه می‌تواند داده‌ها را بخواند/ویرایش کند. برای داده‌های محرمانه یا استفاده تیمی باید احراز هویت و کنترل مجوز جداگانه پیاده‌سازی شود؛ این بسته تنظیمات امنیتی موجود را تغییر نمی‌دهد.
2. **کارهای تکرارشونده** هنگام بسته بودن مرورگر خودکار تولید نمی‌شوند. دکمه «ایجاد نوبت‌های سررسید» باید زده شود. هر الگو در یک اجرا حداکثر ۳۰ نوبت می‌سازد؛ برای سررسیدهای بسیار قدیمی می‌توان دوباره اجرا کرد. افزودن زمان‌بندی خودکار واقعی به Cron/سرویس خارجی نیاز دارد.
3. **تاریخچه** از تغییرات پس از نصب V3 شروع می‌شود؛ رویدادهای قبلی را نمی‌توان حدس زد. در هر پروژه فقط آخرین ۲۵ رویداد ذخیره می‌شود و Snapshotها حجم JSON را افزایش می‌دهند.
4. نمودار «۷ روز اخیر» فقط برای کارهایی است که `completedAt` دارند؛ وظایف قدیمی تکمیل‌شده، تاریخ ثبت تکمیل ندارند و در نمودار تاریخی شمرده نمی‌شوند.
5. هر ذخیره در API به یک GitHub Commit می‌انجامد و ممکن است باعث Deploy جدید Vercel شود؛ برای حجم استفاده زیاد، ساختار دیتابیس/ذخیره‌سازی مستقل مناسب‌تر است.
6. کنترل SHA فقط جلوی برخورد کلاینت‌های V3 را می‌گیرد؛ کلاینت‌های قدیمی بدون هدر هنوز می‌توانند داده را تغییر دهند. برای ویرایش‌های هم‌زمان فراوان، سرویس داده با تراکنش واقعی بهتر است.
7. این نسخه ورود کاربر، سطوح دسترسی، اعلان پوش و زمان‌بند پس‌زمینه ندارد.

## فایل آزمایشی

`project-tracker-v3-demo.html` (جدا از ZIP انتشار): داده‌های **کاملاً ساختگی** دارد، API را در خود مرورگر شبیه‌سازی می‌کند و به پروژه عملیاتی، GitHub یا Vercel وصل نمی‌شود. برای بررسی UI قبل از انتشار باز کنید.
